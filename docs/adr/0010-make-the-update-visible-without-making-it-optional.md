# Make the update visible without making it optional

Surface a waiting update in the app instead of applying it silently, but keep applying it regardless. A dot on the Settings icon in the sidebar footer says an update is staged; an update card at the top of the About page says what it is, what changed, when the app last managed to check, and offers an immediate restart. Neither is a gate. A user who never looks still gets the update on their next launch.

This amends the last paragraph of `docs/adr/0009-distribute-vxfiles-through-per-user-velopack.md`. That decision was right that VxFiles must not wait for a click, and wrong that this means saying nothing. Distribution here depends entirely on auto-update and carries no telemetry, so a silently broken updater is invisible to everyone, forever. The persisted last-checked line on the card exists for that case and is not decoration: it advances only on a check that actually reached GitHub, so that a checker which has been failing for nine days says so instead of reporting a cheerful recent attempt.

The app now re-checks hourly while running, not only on launch. `VelopackApp.Build().Run()` keeps auto-applying a staged update at startup, so a launch check runs against a build that has just updated itself and can only ever report *up to date*; without a periodic check the dot would almost never appear. One check costs one GitHub request against a 60-per-hour ceiling pooled per IP, which is comfortable for a coworker cohort behind one NAT and worth revisiting past roughly forty of them.

Restart-to-update stops killing the process. It arms the Velopack updater with `WaitExitThenApplyUpdates(…, restart: true)` and then closes the window, so the app's ordinary shutdown runs: in-flight file operations drain, the Automation session gets its co-operative cancel, and open tabs are restored unconditionally on the next launch. The previous path called `ApplyUpdatesAndRestart`, which ends in `Environment.Exit(0)` and therefore skipped every one of those — a multi-gigabyte copy died mid-write with a partial file at the destination and no rollback. Install-on-exit and restart-to-update are consequently the same mechanism now, differing only in whether the app comes back, which is what ADR-0009 already implied but was not true when written. No guard or confirmation stands in front of the button, because after this change it is no more destructive than closing the window.

The whole feature is built to keep the downstream layer small, and the shape follows from that rather than from taste. Behaviour changes land in files this fork has already rewritten — `SideloadUpdateService`, `VxFilesEnvironment` — while upstream XAML and view models keep their existing bindings and stay byte-identical. The address-bar update button is therefore kept untouched, inheriting the graceful restart for free through the service beneath it; it is also the only update signal available when the sidebar is in its minimal mode. The new update state lives on a VxFiles-owned `IUpdateStatusService` beside `IUpdateService` rather than inside it, because `IUpdateService` has three implementations and neither the Store nor the dev one can answer questions about Velopack staging. The five inherited booleans become computed projections of that state, so there is one source of truth and nothing upstream has to change to read it.

Three costs are accepted deliberately. The post-update release-notes page keeps its inherited behaviour, so it still needs network at launch and still shows a broken page offline. A failed install remains undetectable, because Velopack applies updates by spawning a detached process and reports nothing. And the rate-limited message cannot name a retry time, since `GithubSource` owns the HTTP client and surfaces only the exception, never GitHub's reset header.
